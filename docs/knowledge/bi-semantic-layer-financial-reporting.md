## Идея, полезная для базы знаний

Ручная финансовая отчетность обычно становится хрупкой, когда каждая таблица
сама извлекает данные, повторяет формулы, исправляет справочники и хранит свою
версию результата. Целевой паттерн разделяет ответственность:

```text
учетные и операционные системы
  -> контролируемая загрузка и проверки качества
  -> хранилище / OLAP-модель (факты, измерения, история)
  -> семантический слой (единые показатели и правила доступа)
  -> web / Excel / LibreOffice как клиенты одной модели
```

«Живой» отчет здесь означает не еще одну вручную собранную копию, а
обновляемое представление поверх общего опубликованного контракта. Excel может
остаться привычным интерфейсом, но не должен быть единственным местом, где
определены бизнес-правила.

## Что должен владеть семантический слой

Минимальный контракт модели включает:

1. **Показатели.** Имя, формула, знак, единица, валюта, округление и владелец.
2. **Зерно.** Что представляет одна строка факта и какие агрегации допустимы.
3. **Измерения.** Период, организация, подразделение, счет, статья, сценарий и
   версионируемые справочники — только если они существуют в реальном домене.
4. **Время и версии.** Фактический период, дата загрузки, версия/сценарий,
   правила закрытого периода и late-arriving corrections.
5. **Связи и фильтры.** Однозначные join-правила без скрытых many-to-many и
   двойного счета.
6. **Доступ.** Row-level/column-level ограничения, чувствительность данных и
   журнал публикации модели.
7. **Наблюдаемость.** Время обновления, freshness SLA, lineage, ошибки качества
   и сверка с контрольным источником.

Расчет, который меняется между книгами Excel, еще не является показателем
семантического слоя. Он становится им после именования владельца, входов,
зерна, правил агрегации, теста сверки и версии.

## Шаблон паспорта показателя

Перед переносом формулы из отчета заполнить один проверяемый паспорт:

| Поле | Требуемый ответ |
| --- | --- |
| Код и название | стабильный machine id и понятное бизнес-имя |
| Назначение и владелец | какое решение поддерживает и кто утверждает смысл |
| Формула и зерно | входы, фильтры, знак, допустимая агрегация |
| Измерения | поддерживаемые разрезы и правила неизвестных значений |
| Период/версия | event date, posting date, close date, actual/plan/forecast |
| Единица/валюта | исходная и отчетная единица, курс и дата курса |
| Источник и lineage | система, таблица/поле, преобразования и версия модели |
| Контроль | эталонная сумма, допуск, freshness и тесты качества |
| Доступ | роли, чувствительные поля и правила экспорта |

Этот шаблон намеренно не задает формулу выручки, прибыли или другого
показателя: ее должен утвердить владелец конкретной финансовой отчетности.

## Оценка текущего `soll_app`

Проверка выполнена только в репозитории, разрешенном задачей.

| Проверка | Фактическое состояние | Вывод |
| --- | --- | --- |
| Финансовый домен | в production-коде нет сущностей выручки, затрат, P&L, бюджета, проводок или план/факта | моделировать нечего |
| API отчетности | `SollApiService` обслуживает задачи, чат, источники, книги, mesh и gadgets; финансового/BI endpoint нет | Android не является источником отчета |
| Локальная модель | Room хранит задачи, sync/tool jobs, заметки, события, устройства, книги и media | не OLAP и не финансовое хранилище |
| BI-зависимости | Gradle содержит Android/Compose/Room/Retrofit/Moshi/media/ML зависимости, но не cube/OLAP/BI client | готового execution path нет |
| Excel | `FilesHandler` только называет `xls/xlsx` «Excel-таблицей» | это не чтение и не live connection |
| Отчеты | `DeviceQaReportFormatter` формирует диагностический Markdown | это не финансовая отчетность |

Итог: в текущем `soll_app` **0 current financial reports**, на которых можно
измерить сокращение ручной сборки. Добавление OLAP SDK, финансовых таблиц или
Excel-парсера в Android было бы новым неподтвержденным продуктовым контуром, а
не внедрением найденной статьи.

## Где размещать возможный пилот

Если финансовые отчеты находятся в другом, отдельно разрешенном backend/BI
репозитории, пилот должен жить рядом с их источником данных и владельцем
метрик. `soll_app` может позднее получать только безопасный агрегированный
snapshot, статус обновления или задачу на явное согласование через существующий
backend-контракт. Он не должен:

- хранить учетные проводки или BI credentials на телефоне;
- дублировать формулы показателей в Compose/Room;
- открывать прямой доступ Android к warehouse/cube;
- считать локальный Excel-файл источником истины;
- публиковать или исправлять финансовые данные без отдельного согласования.

## Шесть ворот пилота

Открывать отдельную задачу на внедрение можно только для одного названного
отчета с владельцем и доступным неперсональным fixture.

1. **Инвентаризация.** Зафиксировать владельца, получателей, периодичность,
   входные файлы/системы, ручные шаги, формулы, время сборки и ошибки минимум за
   несколько сопоставимых закрытий.
2. **Контракт.** Описать зерно, измерения и 3-5 ключевых показателей паспортами;
   назначить источник истины и правила версии/закрытия периода.
3. **Модель.** Собрать изолированный read-only fact/dimension prototype с
   повторяемой загрузкой, ключами, историей справочников и quality checks.
4. **Сверка.** Сравнить каждую сумму и разрез с утвержденным отчетом; хранить
   расхождения и объяснения, а не исправлять их вручную в клиенте.
5. **Live-клиент.** Подключить один web/Excel/LibreOffice клиент к одной версии
   семантической модели; проверить refresh, фильтры, concurrency и доступ.
6. **Продвижение.** Требовать 100% сверку контрольных итогов в согласованном
   допуске, отсутствие критических access/quality дефектов и измеримое снижение
   ручного времени хотя бы на двух последовательных отчетных циклах. Сохранить
   старый процесс как rollback до приемки владельцем.

## Что измерять

Для baseline и пилота нужны одинаковые единицы:

- человеко-минуты от получения входов до готового отчета;
- число ручных копирований, формул и корректировок;
- количество расхождений и повторных выпусков;
- freshness после закрытия периода;
- время refresh и открытия типовых разрезов;
- доля показателей с паспортом, lineage и автоматической сверкой;
- ошибки доступа и экспорт чувствительных данных.

Без baseline нельзя объявлять «автоматизацию», а совпадение красивого dashboard
с одним тестовым файлом не подтверждает корректность семантического слоя.

## Решение о ценности

Источник принят в BI-базу знаний как архитектурный паттерн и преобразован в
**6 adoption gates** для будущего владельца финансовой отчетности. В этом
worktree найдено **0 current financial reports** и получено **0 measured
report-automation value**. Поэтому результат задачи — знание и проверяемый план
оценки; production-интеграция корректно отложена до отдельного разрешенного
репозитория, реального отчета, baseline и владельца метрик.
