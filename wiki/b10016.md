# llama.cpp b10016: подход к интеграции в Soll app

Дата проверки: 2026-07-22.

## Решение

`b10016` не следует внедрять в Android-приложение, Retrofit-контракт или
назначать отдельным runtime default. Релиз добавляет ускоренный Flash Attention
prefill через oneDNN Graph API только для Intel SYCL на Battlemage/Xe2. Это
hardware-specific backend path: неподходящие Intel architecture, tensor shapes
и runtime conditions возвращаются к существующему TILE kernel.

**Текущее решение** — оставить `POST api/v1/chat/turn`,
`soll-backend-route`, Gradle и APK без изменений. Проверяемый standalone
baseline уже pin-ит более новый `b10068`: официальный upstream compare
показывает, что он на `52` commits впереди `b10016`, на `0` commits позади, а
merge base равен точному commit b10016. В активном manifest есть только CPU
targets, а в репозитории нет Intel Battlemage/SYCL execution seam.

**Будущее место интеграции** — server-side inference host за существующим Soll
chat API или изолированный standalone hardware runner. Только этот слой должен
получить checksummed SYCL build, oneAPI/oneDNN configuration и benchmark. В
репозитории соответствующая проверка должна появиться рядом с
`tools/llama-cpp/Test-LlamaCppActiveRelease.ps1`, например как
`Test-LlamaCppSyclBattlemageFlashAttention.ps1`, но не до появления одобренного
Battlemage host и model fixture.

## Что именно изменяет b10016

Новый `fattn-onednn.cpp` строит oneDNN SDPA graph
`MatMul -> Divide -> Add -> SoftMax -> MatMul` и вызывает его из существующего
SYCL Flash Attention dispatch. Путь включён по умолчанию через
`GGML_SYCL_FA_ONEDNN=1`, но применяется только при выполнении узких guard:

1. Устройство — Battlemage/Xe2 (`BMG-G21` или `BMG-G31`); Alchemist и другие
   architecture используют прежний kernel.
2. K/V и mask используют F16, query относится к prefill минимум из `32`
   tokens, а unsupported bias, softcap, sinks и shapes отклоняются.
3. Ошибка oneDNN/SYCL не становится fatal: выполнение возвращается к TILE
   kernel с warning.
4. Для multi-device path выполняется synchronization; single-device остаётся
   без лишнего wait.

Upstream release сообщает ускорение Qwen3.6-27B-Q8_0 prefill в `1.21x` при
`p=512` и `4.26x` при `p=80k`. Эти числа получены на Arc Pro B70 с конкретными
model/toolchain settings и не являются измерением Soll app. В PR также есть
correctness/perplexity проверки, но они не заменяют проверку на целевом Soll
host.

## Пять проверенных seam Soll app

| Seam | Факт в репозитории | Следствие для b10016 |
| --- | --- | --- |
| Android chat contract | `SollApiService.sendChatTurn()` вызывает `POST api/v1/chat/turn` | Не раскрывать SYCL backend Android-клиенту |
| Android runtime policy | `androidRuntimeDefault` — `soll-backend-route`, `packageIntoAndroidApp` — `false` | Не менять APK, Gradle или runtime route |
| Active standalone targets | `llama_cpp_active_defaults.json` pin-ит b10068 и содержит только Android/Windows CPU targets | Не добавлять непроверенный SYCL asset в active default |
| Native integration | В `app/src/main` нет llama.cpp CMake/JNI/C++ или SYCL configuration | В приложении нет execution seam для upstream C++ diff |
| Model provenance | `approved_models.json` использует `deny_unlisted` и содержит `models: []` | Нельзя запускать model-backed benchmark без отдельного approval |

Поиск по production Android source и `tools/llama-cpp` дал `0` текущих match
для `GGML_SYCL_FA_ONEDNN`, Battlemage, Xe2 или oneDNN runtime configuration.
Поэтому production/runtime файлы не меняются.

## Ворота будущего измеримого benchmark

Интеграционный benchmark допустим только после появления реального Intel
Battlemage workload. Он должен:

1. Зафиксировать Battlemage model устройства, driver, oneAPI/oneDNN версии,
   llama.cpp commit/build flags и SHA-256 всех используемых assets.
2. Использовать одобренный GGUF из allowlist и сохранить неизменными model
   revision, quantization, prompt set, seed, context, batch и thread settings.
3. На одном host сравнить `GGML_SYCL_FA_ONEDNN=0` и `=1` с `-fa 1`, измеряя
   prefill tokens/s и TTFT p50/p95 минимум в пяти повторах для короткого и
   длинного context.
4. Проверить output parity или допустимую perplexity delta, `0` crashes,
   invalid tensors, NaN, repeated-token corruption и неожиданных fallback.
5. Для multi-device отдельно проверить synchronization; продвигать путь только
   при устойчивом выигрыше целевой prefill/TTFT не менее `10%` без регрессии
   качества, памяти, температуры или стабильности.
6. Сохранить `soll-backend-route` и текущий checksummed CPU baseline как
   rollback; не включать SYCL binary или model в APK/AAB.
