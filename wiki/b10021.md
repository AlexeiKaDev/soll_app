# llama.cpp b10021: решение о внедрении в Soll app

Дата проверки: 2026-07-22.

## Решение

`b10021` не следует отдельно внедрять в Android-приложение или назначать новым
runtime default. Релиз меняет только построение графа модели DeepSeek-V4:
вместо отдельных `ggml_get_rows()` для предыдущей и текущей частей KV/score
state upstream один раз получает все строки по `state_read_idxs`, а затем
создаёт нужные views. Автор PR указывает сокращение graph splits с `5` до `2`.

В текущем Soll app нет DeepSeek-V4 workload, собственного llama.cpp JNI/CMake
слоя или прямого model execution из Android. Android продолжает отправлять chat
turn через `POST api/v1/chat/turn`, policy оставляет `soll-backend-route`
default и не упаковывает llama.cpp binary в APK. Проверяемый standalone
baseline уже pin-ит более новый `b10068`: официальный upstream compare
показывает, что он на `47` commits впереди `b10021`, на `0` commits позади, а
merge base равен точному commit b10021. Поэтому отдельное обновление или
production-изменение не создаёт измеримой ценности.

Сигнал отклонён для текущего внедрения и остаётся только кандидатом на отдельный
DeepSeek-V4 benchmark после появления одобренной модели и target host.

## Что именно изменяет b10021

До изменения DeepSeek-V4 graph отдельно вызывал `ggml_get_rows()` для
`kv_prev`, `score_prev`, `kv_cur` и `score_cur`. После изменения:

1. `n_read` фиксирует общий размер `ratio * n_blocks`.
2. `kv_rows` один раз получает KV строки по полному `state_read_idxs`.
3. `score_rows` один раз получает score строки по тому же индексу.
4. Previous и current tensors создаются как разные `ggml_view_2d()` над этими
   двумя общими результатами и затем получают прежнюю 3D shape.
5. Выходной `ggml_concat()` и model contract не меняются; цель PR — уменьшить
   число graph splits с `5` до `2`.

Изменение model-specific и потенциально уменьшает overhead исполнения графа,
но upstream PR не публикует benchmark latency, throughput, memory или список
проверенных backend. Из release signal нельзя выводить ускорение Soll app.

## Пять проверенных seam Soll app

| Seam | Факт в репозитории | Следствие для b10021 |
| --- | --- | --- |
| Android chat contract | `SollApiService.sendChatTurn()` вызывает `POST api/v1/chat/turn` | Не добавлять direct model runtime в Retrofit |
| Android runtime policy | `androidRuntimeDefault` — `soll-backend-route`, `packageIntoAndroidApp` — `false` | Не менять APK, Gradle или runtime route |
| Native integration | В `app/src/main` нет собственного llama.cpp CMake/JNI/C++ слоя | Upstream C++ diff не имеет Android execution seam |
| Standalone baseline | `llama_cpp_active_defaults.json` pin-ит `b10068`, который на `47` commits впереди и `0` позади b10021 | Fix уже присутствует в проверяемом baseline |
| Model provenance | `approved_models.json` использует deny-by-default и содержит `models: []` | DeepSeek-V4 runtime smoke сейчас не разрешён |

Поиск в production source и llama.cpp tooling также дал `0` текущих
DeepSeek-V4 model/config match. Поэтому production/runtime файлы не меняются.

## Ворота будущего измеримого benchmark

Отдельный benchmark допустим только после появления реального DeepSeek-V4
workload. Он должен:

1. Зафиксировать target host, backend, llama.cpp commit, model revision,
   quantization, GGUF SHA-256 и одобрение модели в allowlist.
2. Сравнить parent `d3fba0c79db8d25a76031783bf071d02234812e6` с b10021
   или отдельно доказать наличие commit b10021 в тестируемом b10068 binary.
3. На одинаковых prompts, seed, context и thread/device settings измерить graph
   splits, prompt/generation tokens/s и end-to-end latency p50/p95 минимум в
   пяти повторах.
4. Подтвердить output parity на deterministic prompts; crashes, invalid tensors,
   NaN и unexpected fallback должны быть равны `0`.
5. Продвигать изменение только при устойчивом выигрыше целевой latency не менее
   `10%` без регрессии качества, памяти, температуры или стабильности.
6. Сохранить `soll-backend-route` и текущий checksummed b10068 baseline как
   rollback; не включать model или binary в APK/AAB без отдельного review.
