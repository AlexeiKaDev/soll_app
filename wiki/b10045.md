# llama.cpp b10045: место внедрения в Soll app

Дата проверки: 2026-07-19.

## Решение

Изменение `b10045` относится к server-side управлению состоянием
`llama-server`, а не к Android UI, Retrofit-контракту или локальному JNI.
**Место продуктового внедрения** — inference adapter Soll server за существующим
Android-контрактом `POST /api/v1/chat/turn`: только этот слой должен связывать
`session_id` с llama slot, вызывать `/slots/{id}?action=save|restore|erase` и
владеть файлами snapshot. Код этого server-side adapter отсутствует в данном
изолированном репозитории, поэтому production-реализация здесь не добавляется.

**Место проверки в этом репозитории**, если появится одобренный workload, —
отдельный smoke `tools/llama-cpp/Test-LlamaCppMultimodalSlotPersistence.ps1`
рядом с `Test-LlamaCppActiveRelease.ps1`. Smoke не создаётся в этой задаче:
`approved_models.json` сейчас deny-by-default и содержит `0` моделей, а
проверенного multimodal GGUF + `mmproj` fixture нет.

Текущий `b10068` verification baseline уже содержит commit `b10045`: upstream
compare показывает `b10068` на `23` commit впереди и `0` commit позади, с
`a8dc0e3269a5378d212e6daea953fbbaa7ac8e4b` как merge base. Повышать версию,
менять `soll-backend-route` или включать binary/model в APK ради этого сигнала
не нужно.

## Что исправляет b10045

При загруженном `mmproj` старый `llama-server` проверял capability всего model
context и отвечал HTTP `501` на slot save/restore/erase даже для чисто текстовой
истории. В результате downstream не мог повторно использовать сохранённый
prefill cache для длинного text-only prompt на multimodal model.

`b10045` меняет gate на фактическое содержимое slot:

1. `server_tokens::has_media()` показывает наличие image/audio chunks.
2. `check_slot_no_media()` разрешает операцию для text-only slot независимо от
   загруженного `mmproj`.
3. Save получает tokens через `get_text_tokens()` после проверки отсутствия
   media.
4. Text-only save/restore/erase разрешены; slot с media по-прежнему должен быть
   отклонён с HTTP `501`.
5. Сериализация image/audio chunks не добавлена и не является частью релиза.

Это correctness/capability fix для узкого server workload, а не общий прирост
скорости Android inference. Экономия TTFT появляется только если consumer уже
сохраняет и восстанавливает длинный text-only prefix через llama slot API.

| Seam | Наблюдение | Решение |
| --- | --- | --- |

## Контракт будущего server-side adapter

Если Soll server получит одобренный local `llama-server` с multimodal model,
adapter за `POST /api/v1/chat/turn` должен:

1. Хранить отображение `session_id -> slot_id/snapshot` только на server side и
   изолировать snapshot между пользователями и сессиями.
2. Восстанавливать snapshot перед text-only turn, если его версия, model hash,
   server build и prompt prefix совпадают.
3. Сохранять slot после успешного text-only turn; не пытаться сериализовать slot
   с image/audio chunks.
4. Считать HTTP `501` ожидаемым защитным результатом для media slot, а не
   fallback к небезопасному сохранению только части multimodal state.
5. Удалять snapshot при удалении/сбросе сессии и ограничивать путь, размер,
   TTL и права доступа к файлам.
6. При restore failure безопасно выполнить полный prefill, не меняя публичный
   `api/v1/chat/turn` response contract.

Android `ChatViewModel`, `SollRepository` и `SollApiService` при таком внедрении
не меняются.

## Ворота измеримого smoke

Отдельный implementation task допустим только после pin одобренных model GGUF,
`mmproj`, llama.cpp commit и target host. Focused smoke должен доказать:

1. text-only save, restore и erase возвращают `2xx` при загруженном `mmproj`;
2. save slot с реальным image/audio content возвращает HTTP `501`;
3. restored text tokens и продолжение совпадают с control без snapshot;
4. snapshot одной session нельзя восстановить как snapshot другой session;
5. на одинаковых длинных prompts измерены cold и restored TTFT p50/p95 минимум
   в пяти повторах, а crashes, invalid state и cross-session reuse равны `0`.

До такого smoke наблюдаемая runtime-ценность для Soll app равна `0`; ценность
этой задачи — точная локализация внедрения без ненужного изменения Android и
без дублирования уже включённого upstream fix.
