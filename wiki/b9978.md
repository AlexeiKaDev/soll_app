# llama.cpp b9978: решение о внедрении в Soll app

Дата проверки: 2026-07-26.

## Решение

Source signal **валидирован и релевантен** как продолжение уже принятого в
Soll_app server-side regression contract для context checkpoints. `b9978`
исправляет плотное накопление checkpoints в длинном multi-turn workload:
старые checkpoints, нарушающие `checkpoint_min_step`, удаляются перед
добавлением нового, а checkpoints текущей task сохраняются, чтобы последний
checkpoint не удалял предпоследний в том же prompt processing.

Текущее решение — принять исправление только как regression knowledge и **не
менять production/runtime**. Android продолжает отправлять chat turn через
`POST api/v1/chat/turn`, standalone llama.cpp не упаковывается в APK, а
активный checksummed baseline `b10068` уже содержит `b9978`. Локального
model-backed workload, который включает context checkpoints и измеряет их
поведение, в репозитории нет.

## Что исправляет b9978

Issue #25023 описывает длинный agent conversation с включёнными context
checkpoints. `is_last_user_message` разрешал создавать checkpoint на каждом
turn даже внутри `checkpoint_min_step`; при ограниченном числе slots это
сжимало покрываемое checkpoint window и могло приводить к полному повторному
prefill более раннего контекста.

После b9978:

1. `common_prompt_checkpoint` хранит optional `id_task`.
2. `create_checkpoint()` получает id текущей server task.
3. Перед добавлением checkpoint удаляются checkpoints предыдущих tasks,
   расположенные не дальше `checkpoint_min_step` от более раннего сохранённого
   checkpoint.
4. Checkpoints текущей task не удаляются этим проходом, поэтому два
   checkpoints около конца одного prompt не вытесняют друг друга.
5. `near_prompt_end` может создать критический checkpoint даже внутри
   min-step; новому checkpoint записывается текущий `id_task`.

Исправление не отключает checkpoints на user boundaries. Оно восстанавливает
spacing invariant между старыми tasks, одновременно сохраняя пару
checkpoints, созданных текущей task около конца prompt.

## Связь с уже принятой b9936 knowledge

`docs/knowledge/llama-cpp-b9936-min-step-prompt-batch-splitting.md` фиксирует
PR #25420: промежуточная user boundary не должна дробить prefill batch, если
checkpoint всё равно нарушил бы `checkpoint_min_step`.

`b9978` относится к тому же `tools/server/server-context.cpp`, но закрывает
следующий участок lifecycle: уже сохранённые checkpoints не должны образовать
плотный кластер между последовательными server tasks, а checkpoint около
конца prompt должен быть создан и сохранён. Поэтому сигнал релевантен будущему
локальному inference, но не создаёт отдельный Android feature или API field.

## Проверенные seam Soll app

| Seam | Наблюдаемый факт | Решение |
| --- | --- | --- |
| Android chat contract | `SollApiService.sendChatTurn()` вызывает `POST api/v1/chat/turn` | Не раскрывать checkpoint flags в Retrofit |
| Android runtime policy | `androidRuntimeDefault=soll-backend-route`, `packageIntoAndroidApp=false` | Не менять APK, Gradle или runtime route |
| Active standalone baseline | b10068 на `90` commits впереди b9978, на `0` позади; merge base равен exact b9978 commit | Не делать downgrade или отдельный rollout b9978 |
| Release smoke | `Test-LlamaCppActiveRelease.ps1` исполняет только `llama-server --version` | Текущий smoke не выдаётся за checkpoint workload |
| Model gate | Deny-by-default tiny fixture разрешён только для b9945/b9947 smoke | Нет одобренного long-context server fixture |
| Existing knowledge | b9936 уже документирует min-step prompt-batch seam | b9978 добавляет complementary checkpoint-lifecycle contract |

Реализация inference backend за `soll-backend-route` отсутствует в этом
worktree. Поэтому оценка не утверждает, какие checkpoint flags или llama.cpp
build используются удалённым backend. Production source, release defaults,
model allowlist и Android contract остаются без изменений.

## Будущий измеримый smoke

Model-backed smoke нужен только после одобрения long-context GGUF и target
host. Он должен:

1. Зафиксировать model revision и SHA-256, chat template, backend, context,
   seed и два exact build: parent
   `6b4dc2116a92c5c8f2782bfe51fabe5ee66fb5ef` и b9978 либо b10068 с
   доказанной ancestry.
2. Запустить `llama-server` с context checkpoints, например
   `--ctx-checkpoints 8 --checkpoint-min-step 8192`, и сохранить effective
   flags без секретов или prompt content.
3. Проиграть deterministic multi-turn fixture с несколькими server tasks,
   близкими user/tool boundaries и отдельным `near_prompt_end`.
4. По instrumentation подтвердить: старые меж-task checkpoints внутри
   min-step удалены, checkpoints текущей task сохранены, near-end checkpoint
   создан, а checkpoint window не схлопывается.
5. Повторить workload минимум `5` раз на каждом build и сравнить число полных
   re-prefill, cache-hit ratio, покрытие checkpoint window, prompt tokens/s и
   TTFT; promotion требует `0` неожиданных full resets.
6. Подтвердить одинаковые response schema/token result при фиксированном seed,
   `0` crashes, `0` decode errors и `0` cross-session/task leakage.

До появления такого fixture выполняется только repository contract test; он
не считается model-backed runtime smoke.
